# E2E-1 — Order Lifecycle UI Bot (QR → POS → KDS)

One orchestrated Playwright test drives the **real** frontends through the full
order lifecycle as three actors on three emulated devices, asserting real-time
propagation at each cross-app handoff:

> Customer places an order on the QR menu → waiter confirms on POS → kitchen
> Starts/Readies on KDS → status flows back to POS (push) and the QR screen (poll).

This `e2e/` workspace is standalone — it spans all apps and belongs to none.

---

## What's here

```
e2e/
  playwright.config.ts     3-actor harness; trace + video ON; globalSetup
  global-setup.ts          mints POS+KDS sessions via the API → artifacts/session.json
  config/env.ts            deployment URLs (override via env)
  helpers/
    api.ts                 pin-login + /auth/me (JWT minting, no UI)
    storage.ts             builds localStorage storageState + IndexedDB device-secret injectors
    actors.ts              device descriptors + per-actor context/trace/video
  tests/
    order-lifecycle.spec.ts  the golden path (3 contexts, 1 test)
  fixtures/seeded.json     generated by `pnpm db:seed:e2e` (git-ignored)
```

The deterministic test fixtures are produced by an **API-side** seed augmentation,
`api/prisma/seed-e2e.ts` (script `db:seed:e2e`). The stock seed mints device
secrets and PINs at random and leaves table QR tokens unset, so this step writes
E2E-only values **we choose** (fixed device secret, known PINs via the real
argon2+HMAC hashers, a fixed `qrIdentifier` on table **t6**) and enables QR
customer ordering. It writes everything the harness needs to `e2e/fixtures/seeded.json`.

## Prerequisites

1. The six apps are built and running behind the Tailscale + nginx host from
   `DEPLOY.md` (default `https://msi.tail8514ca.ts.net`), **with the data-testid
   changes in this branch built in** (the apps inline at build time — rebuild
   `customer`, `pos`, `kds` after pulling).
2. Postgres reachable; the main seed has run.
3. Node 20+ and Playwright's chromium.

## Run

```bash
# 1) Seed the database (deterministic fixtures) — in the api workspace
cd api
pnpm docker:up                 # Postgres (+ Redis)
pnpm prisma:deploy             # apply schema
pnpm db:seed                   # main deterministic seed (tenant/branch/table/menu/staff)
pnpm db:seed:e2e               # E2E fixtures → ../e2e/fixtures/seeded.json

# 2) Run the test — in the e2e workspace
cd ../e2e
pnpm install
pnpm install:browsers          # playwright install chromium
pnpm test:headed               # headed (watchable); use `pnpm test` for headless
```

Point at another deployment by overriding env before `pnpm test`:

```bash
E2E_HOST=https://your-host.ts.net pnpm test
# or finer-grained: E2E_API_BASE_URL=...   (defaults to $E2E_HOST/res/api)
```

## The flow it asserts (and the real channels)

| Step | Actor | Assertion | Channel |
| --- | --- | --- | --- |
| Place order on t6 (Pork khorovats + required modifiers) | QR (mobile) | order-status screen shows | — |
| New order appears | POS (tablet) | `request-card` for «Պատշգամբ 2» in the open panel | **WS** `order_request.new` |
| Waiter confirms | POS | order page opens (`pos-order-status`) | `POST /order-requests/{id}/confirm` |
| Customer learns it's confirmed | QR | `order-status` → `CONFIRMED` | **poll** (4 s) `GET /public/order-requests/:id` |
| Ticket arrives | KDS (desktop) | `kds-ticket` for «Պատշգամբ 2» | **WS** `kds:ticket.new` |
| Start → Ready | KDS | `kds-item` → `PREPARING` → `READY` | `POST /kds/order-items/{id}/preparing` · `/ready` |
| Completion propagates back | POS | `pos-order-status` → `READY` | **WS** `order.updated` / `order.ready` |

All cross-app assertions auto-wait on a **pushed** UI change (no reloads, no sleeps;
generous `HANDOFF` timeout). The QR app has no WebSocket — its back-propagation is
the 4 s poll, and it only ever observes `CONFIRMED` (never kitchen progress), which
is why kitchen completion is asserted on **POS**, per the real implementation.

## Auth bootstrap (how a test reaches authenticated POS/KDS)

POS/KDS use device-anchored staff auth (device secret in IndexedDB + 6-digit PIN).
The harness avoids the PIN UI entirely:

1. `db:seed:e2e` registers a fixed device secret (only `sha256(secret)` is stored)
   and a known PIN (real argon2id + HMAC fingerprint) for the flagship waiter (POS)
   and kitchen staff (KDS).
2. `global-setup` calls `POST /auth/pin-login` (+ `/auth/me` for KDS) to mint JWTs,
   and builds the exact `localStorage` (`pos-auth`/`pos-branch`;
   `kds-auth`/`kds-branch`/`kds-station`) the apps read on boot.
3. The spec injects that `storageState` and writes the device secret into IndexedDB
   (`pos-device`/`kds-device`), then reloads once so the enrollment gate hydrates as
   "enrolled". The context lands authenticated on the home screen.

## data-testid added (critical path only — no blanket sweep)

customer: `menu-root`, `dish-card-<id>`, `item-sheet`, `modifier-group`,
`modifier-option`, `add-to-cart`, `open-cart`, `cart-view`, `place-order`,
`order-status` (+ `data-status`).
pos: `requests-bell`, `requests-badge`, `requests-panel`, `request-card`
(+ `data-table-name`), `request-confirm`, `open-confirmed-order`,
`pos-order-status` (+ `data-status`).
kds: `kds-board`, `kds-ticket` (+ `data-order-number`/`data-all-ready`),
`kds-item` (+ `data-status`), `kds-item-start`, `kds-item-ready`, `kds-order-ready`.

## Scope (v1)

Golden path only. Out of scope (E2E-2+): waiter rejection/cancel, multi-item /
multi-modifier orders, payment/checkout, offline ordering, multi-branch, and the
device matrix. Prove the harness here, then branch.
